# Blog 仕様

「よりストック型の、フローしないブログ」をコンセプトとした 4 つ目のコンテンツタイプ **Blog** の仕様を定義する。Obsidian Vault の `Blog/` フォルダをソースとし、**タグの組み合わせ自体がページ (URL) となる**点が、既存の Notes / Glossary / Books と根本的に異なる。

本ドキュメントは Blog 固有の仕様に限定する。frontmatter スキーマの全体像は `docs/content-spec.md`、レイアウトの基本は `docs/ui-spec.md`、ビルドパイプラインは `docs/build-spec.md` を参照。

## コンセプト

- 時系列で「流れていく」通常のブログではなく、タグのネットワークによって記事を回遊させる構造を取る
- 個々の記事は **タイトルを持たず**、付与されたタグの組み合わせが実質的なタイトルとなる
- 記事は個別の詳細ページを持たない。常に「タグの組み合わせページ内のひとつのブロック」として表示される

## ソースとデータモデル

### 配置

| 項目         | 内容                                                          |
| ------------ | ------------------------------------------------------------- |
| Vault 内パス | `Blog/` (設定ファイルで指定)                                  |
| 構造         | フラット (サブフォルダなし)。ファイルは `Blog/` 直下に置く    |
| 除外         | Notes 収集の `exclude` に `Blog/**` を追加する                |

### ファイル名 = 作成日時 (source of truth)

記事の**作成日時はファイル名を唯一の正**とする。frontmatter に `created` は持たせない (二重管理を避けるため)。

- フォーマット: `YYYY-MM-DD HHmm` (例: `2025-12-11 0930.md`)
  - Obsidian / OS のファイル名制約のため `:` は使わず、時刻は 4 桁連結 (`HHmm`) とする
  - タイムゾーンはサイトロケール (JST 固定、`site.config.ts` で上書き可) として扱う
- 用途:
  - **並び順**: Blog 内のすべての一覧は作成日時降順。時刻まで含むため同日複数記事も安定ソートされる
  - **表示**: 記事ブロックに表示する「作成日」はファイル名の日付部分を `YYYY/MM/DD` に整形したもの
  - **アンカー**: ファイル名から各記事の HTML アンカー id を生成する (後述)
- 一意性: 同一フォルダ内でファイル名は重複できないため、作成日時は自然に一意となる

### frontmatter スキーマ

Blog ではすべてのメタデータを **必須** とする (既存タイプは `status` 等が任意だが、Blog は明示を要求する)。

| キー      | 型              | 必須 | 説明                                                                     |
| --------- | --------------- | ---- | ------------------------------------------------------------------------ |
| `tags`    | string[]        | 必須 | 1〜4 個。フラットタグのみ (`/` 禁止)。実質的なタイトルを兼ねる            |
| `updated` | date (ISO 8601) | 必須 | 更新日。sitemap の `lastmod`、グローバルトップの「最近更新」、feed に使用 |
| `status`  | enum            | 必須 | `published` / `draft` / `archived`。`draft` / `archived` は完全に除外    |

- `title` / `summary` / `featured` / `created` は **持たない**
  - タイトル: タグの組み合わせが代替する
  - サマリー: feed 等で必要な抜粋はビルド時に本文先頭から自動生成する
  - Featured: Blog は Featured セクションの対象外
  - created: ファイル名から取得 (上記)

### バリデーション (build.strict)

以下はビルドエラーとする。

- ファイル名が `YYYY-MM-DD HHmm` 形式でない / 無効な日時
- `tags` が空、または 5 個以上 (**1 記事あたり最大 4 タグ**)
- タグ名に `/` を含む (フラットタグのみ)
- タグ名に `+` を含む (タグ集合 URL の区切り文字と衝突するため)
- タグ名が予約語 `page` (ページネーション用セグメントと衝突するため)
- `updated` / `status` の欠損・型不一致・enum 違反

警告 (継続) とするもの: 本文が空。

## タグ

### 名前空間

タグはコンテンツタイプごとに独立した名前空間を持つ。Blog の `#react` は Notes / Glossary / Books の `#react` とは別物として扱い、URL も `/blog/tags/react` で分離する。

### フラットタグ

Blog タグは**フラット**のみをサポートする。既存タイプの階層タグ (`frontend/react`) は Blog では使用しない。`/` はパス区切り、`+` はタグ集合 URL のタグ連結に使うため、タグ名に `/` および `+` を含めることは禁止する。

### 並び順 (正規形の基準)

タグの並び順は **Unicode コードポイント昇順** とする。

- 左サイドツリーの同階層内のソート、および「それ以外のタグ」併記時の順序に一律で適用する
- Latin → カタカナ → 漢字 の順になる (例: `UI-UX` < `スターウォーズ` < `デザインシステム` < `マイクロコピー` < `ライティング` < `映画`)
- この順序がタグ集合の **正規形 (URL に用いる唯一の並び)** を一意に決定する

## URL 構造

トレイリングスラッシュなし。

| URL                              | 内容                                                                          |
| -------------------------------- | ----------------------------------------------------------------------------- |
| `/blog`                          | トップページ (全公開記事を作成日時降順)                                        |
| `/blog/page/[n]`                 | トップのページネーション (`n` は 2 以上)                                       |
| `/blog/tags/[tagset]`            | タグ詳細ページ。`tagset` はタグ集合 (1〜4 個) を正規形で `+` 連結した単一セグメント |
| `/blog/tags/[tagset]/page/[n]`   | タグ詳細のページネーション (`n` は 2 以上)                                     |
| `/blog/feed.xml`                 | Blog 専用 Atom フィード                                                        |

- `tagset` はタグ集合を表す **単一セグメント**で、所属タグをコードポイント昇順 (正規形) に並べ `+` で連結する。例: `{映画, スターウォーズ}` → `スターウォーズ+映画`
  - パスセグメント内の `+` はリテラル文字 (クエリ文字列で空白に変換される挙動とは別で、`decodeURIComponent` でも変化しない)。安全にタグ区切りとして使える
  - 各タグ名自体は URL にそのまま用いる (日本語可、`/notes` 等と同様に非エスケープ)。`+` をタグ名に含めることは禁止 (バリデーションで弾く)
- タグ集合ごとに生成するページは **正規形 1 つだけ**。非正規 (未ソート) のトークンは生成しないため到達時は 404 となる (詳細は後述)
- `/blog/tags` (タグなし) は生成しない。タグ一覧は左サイドツリーが担う
- `page` はページネーション専用の予約セグメント。タグ名に `page` は使えない (バリデーションで弾く)

### タグ詳細ページの絞り込み条件

`tagset` のタグ集合を S とすると、そのページには **S を部分集合として含む (タグ集合 ⊇ S) すべての公開記事**を作成日時降順で表示する。

- 例: `/blog/tags/映画` → タグに `映画` を含む全記事
- 例: `/blog/tags/スターウォーズ+映画` → `映画` と `スターウォーズ` の**両方**を含む全記事 (他のタグを併せ持っていてもよい)

### 集合ごとに単一ページ (正規形)

タグ集合 S が同一で `+` の並び順だけが異なる表記 (順列) は絞り込み結果が完全に一致するため、**タグ集合ごとに正規形のページを 1 つだけ生成**し、順列の重複ページは生成しない。

- **正規形** = S のタグを **コードポイント昇順**に並べ `+` で連結した `tagset` セグメント
- 同一集合の別順序 (`+` の並びが昇順でない) は生成しない。到達時は (静的サイトのため) 404 とする
- 後述の左サイドツリー・パンくず・「それ以外のタグ」などサイト内のリンクは**すべて正規形 URL を指す**ため、非正規 URL は外部リンクや手入力でのみ発生する
- 例: `{スターウォーズ, 映画}` のページは `/blog/tags/スターウォーズ+映画` ただ 1 つ (`ス` < `映`)

`rel=canonical` や noindex といった重複ページ向けの SEO 制御は不要となる (重複ページ自体を作らないため)。

> [!note]
> 「同一記事が複数のタグ集合ページに載る」重複は依然として残る (例: `{a, b, c}` の記事は `{a}` `{a, b}` `{a, b, c}` 等すべての部分集合ページに出現する)。ただしこれらは**絞り込み結果が異なる別ページ**であり、内容が完全一致する「順列の重複」とは異なる。検索インデックスの重複排除のみ後述の対応が必要で、canonical は不要。

#### 生成するタグ集合ページの定義

- タグ集合 S について「S を部分集合として含む公開記事が 1 件以上存在する」とき、かつそのときに限り `/blog/tags/[S の正規形]` を生成する
- 1 記事のタグ数は最大 4 なので、生成対象 S のサイズは自然に 1〜4 に収まる
- ある集合 S のページが存在するなら、S の任意の部分集合のページも必ず存在する (同じ記事がその部分集合の上位集合になるため)。これによりパンくずの累積リンク (後述) は常に到達可能
- ビルド削減: 1 記事 (m タグ) あたり、順列ベースの ΣP(m, k) (m=4 で 64 経路) から部分集合ベースの 2^m − 1 (m=4 で 15) へ減る。サイト全体では集合の重複排除でさらに減少する

### sitemap / 検索への反映

- **sitemap**: 生成したすべてのタグ集合ページ (とそのページネーション) および `/blog`・`/blog/page/[n]` を含める。各ページは絞り込み結果の異なる固有ページなので、すべて掲載対象
- **検索 (Pagefind)**: 同一記事が複数のタグ集合ページに重複出現するため、各記事本文のインデックス対象は**その記事の全タグ集合ページ (= 最も特定的な正規形ページ) の 1 箇所のみ**とする。他のページ (より広い部分集合ページ・`/blog` 系) では当該記事ブロックを `data-pagefind-ignore` にする。検索結果のリンク先は全タグ集合ページ + 記事アンカー

## 左サイドメニュー (タグツリー)

Blog 選択時、左サイドバーにはファイルツリーではなく**タグの共起ツリー**を表示する。

### 構築ルール

記事が持つタグの**共起の順列**を展開する。

- **トップレベル**: 公開記事で使われている全タグ (重複なし)
- **2 階層目以降**: あるノードのパスを `[t1,…,tk]` とすると、その子は「`{t1,…,tk}` を含む記事が併せ持つ、`t1…tk` 以外のタグ」。各子について再帰的に展開する
- ノード `[t1,…,tk]` は「`{t1,…,tk}` を含む公開記事が 1 件以上存在し、かつ `k ≤ 4`」のときに限り生成する
- 同階層の兄弟はコードポイント昇順でソートする
- 最大タグ数が 4 のため、ツリーの最大深さは 4 段

複数タグを持つ記事は、各タグがトップレベルに現れ、その配下に残りのタグがネストされるため、項目は意図的に重複する (下記イメージ参照)。

#### イメージ A (記事例: `{UI-UX, マイクロコピー, ライティング}` `{UI-UX, デザインシステム}` `{UI-UX}` `{スターウォーズ, 映画}`)

```
- UI-UX
  └ デザインシステム
  └ マイクロコピー
    └ ライティング
  └ ライティング
    └ マイクロコピー
- スターウォーズ
  └ 映画
- デザインシステム
  └ UI-UX
- マイクロコピー
  └ UI-UX
    └ ライティング
  └ ライティング
    └ UI-UX
- ライティング
  └ UI-UX
    └ マイクロコピー
  └ マイクロコピー
    └ UI-UX
- 映画
  └ スターウォーズ
```

> 元の手描きイメージではトップレベルの一部 (`マイクロコピー` / `ライティング` 配下) が 2 階層までしか描かれていなかったが、ルール上は最下層まで完全展開する。上記が正となる。

### ツリーの挙動

- 各タグノードはリンクであり、クリックでそのノードのタグ集合の**正規ページ**へ遷移する。ツリー上の表示順 (順列) に関わらず、リンク先 URL は常にコードポイント昇順の `+` 連結正規形となる
  - 順列ツリーは意図的な重複を残し「同一集合への複数の入口」= 回遊性を担保するが、行き先 (ページ) は集合ごとに 1 つに収束する
- **アクティブ表示 (ハイライト)**: 現在ページのタグ集合と一致する**すべてのノード**に付与する。URL のタグ集合から導出する**ステートレスな処理**とし、遷移経路には依存しない
  - 非正規順のノードをクリックして正規ページへ遷移しても、クリック元ノードは一致集合に含まれるため点灯したままとなる。強調が別の枝へ「移動」することはなく、正規順の双子ノードが追加で点灯するだけ
- **展開 (開閉)**: ハイライトとは独立に扱う
  - クライアント遷移中はユーザーの開閉状態を保持する。操作していた枝が開いたまま残り、クリック元の点灯ノードが可視のまま維持される
  - コールド読み込み (リロード・外部リンクで正規 URL に直接到達) 時は、現在集合の**正規チェーンのみ**を既定展開する
  - 一致する順列の双子ノードを強制展開はしない (複数枝が一斉に開いて賑やかになるのを避ける)
- ツリー上部に検索 (フィルタ) 入力を置き、タグ名でツリーをフィルタする (既存ツリーと同様)
- react-aria-components の Tree を用い、キーボード操作・ARIA 属性を付与する

## ページ仕様

### 記事ブロックの構成

トップページ・タグ詳細ページとも、各記事を以下の構成のブロックとして縦に並べる。ブロック間は区切り線 (`---`) で仕切る。

1. **作成日** — `YYYY/MM/DD` (ファイル名の日付部分)
2. **それ以外のタグ** — 現在ページのタグ集合に含まれないタグを併記 (リンク)。該当タグがなければ省略
3. **本文** — Markdown を変換した HTML (拡張記法は後述)

「それ以外のタグ」が実質的に通常ブログの記事タイトルの役割を果たす。

### トップページ (`/blog`)

- パンくず: `Blog`
- 全公開記事を作成日時降順で表示
- 各記事の「それ以外のタグ」= その記事の**全タグ** (現在ページのタグ集合が空のため)。コードポイント昇順で併記
- 10 件ごとにページング (`/blog/page/[n]`、「次へ」「前へ」のみ)

#### イメージ C (トップの記事タグをクリックした先 = 正規タグページ `/blog/tags/UI-UX+マイクロコピー+ライティング`)

```
Blog › #UI-UX › #UI-UX#マイクロコピー › #UI-UX#マイクロコピー#ライティング (パンくず)

#UI-UX#マイクロコピー#ライティング (ページタイトル)

2025/12/11

{本文}

---

2025/04/09

{本文}
```

### タグ詳細ページ (`/blog/tags/…`)

- パンくず: 累積正規チェーン `Blog / #t1 / #t1#t2 / … / #t1#t2…tk` (タグ集合をコードポイント昇順に並べ、先頭から 1 つずつ足した部分集合を順に表示)
  - 各要素はその部分集合の正規ページへリンクする (表示は `#` 連結、リンク先 URL は `+` 連結の正規形)。末尾要素は現在ページ
  - 生成定義より部分集合ページは必ず存在するため、各リンクは常に到達可能
- ページタイトル: `#t1#t2…` (集合のタグをコードポイント昇順で併記)
- 絞り込み: タグ集合 ⊇ このページのタグ集合 となる公開記事を作成日時降順で表示
- 各記事の「それ以外のタグ」= 記事のタグ集合からこのページのタグを除いた残り。コードポイント昇順で併記
- 10 件ごとにページング (`/blog/tags/[tagset]/page/[n]`)

#### イメージ B (`/blog/tags/UI-UX`)

```
Blog › #UI-UX (パンくず)

#UI-UX (ページタイトル)

2025/12/11
#マイクロコピー#ライティング

{本文}

---

2025/10/29
#デザインシステム

{本文}

---

2025/07/24

{本文}

---

2025/04/09
#マイクロコピー#ライティング

{本文}
```

`2025/07/24` は `#UI-UX` のみを持ち「それ以外のタグ」が存在しない記事の例。

### 記事アンカー

各記事ブロックは、ファイル名 (作成日時) 由来の安定したアンカー id を持つ。全ページで同一の id を用いる。

- 例: ファイル `2025-12-11 0930.md` → `id="p-2025-12-11-0930"` (空白等は URL/HTML 安全な文字へ正規化)

### リンク遷移ルール

「それ以外のタグ」クラスタおよびトップページの記事タイトル相当クリック時の遷移先を以下で統一する。

現在ページのタグ集合を P、クリック対象の併記タグ群を R とすると、

> 遷移先 = `/blog/tags/` + (P ∪ R をコードポイント昇順で `+` 連結した正規形) [ + `/page/[n]` ] + `#記事アンカー`

- 遷移先は常にタグ集合 P ∪ R の**正規ページ**。集合の和を取って正規形に整えるだけなので、常に生成済みのページへ着地する
  - 例 1: `/blog/tags/映画` で `#スターウォーズ` をクリック → `/blog/tags/スターウォーズ+映画`
  - 例 2: `/blog/tags/UI-UX` で `#マイクロコピー#ライティング` をクリック → `/blog/tags/UI-UX+マイクロコピー+ライティング`
- **トップページから**: P は空集合のため、遷移先は「記事の全タグをコードポイント昇順に並べた正規ページ」+ 該当記事アンカーとなる
  - 例: トップの `2025/12/11` の `#UI-UX#マイクロコピー#ライティング` をクリック → イメージ C の `2025/12/11` の位置へ
- 「それ以外のタグ」併記は 1 クリックで R 全体を追加する単位とする (タグ個別ではなく、クラスタごと)
- 遷移先で対象記事が 2 ページ目以降にある場合、リンクは正しい `/page/[n]` + アンカーを指す (ビルド時に算出)

### ページネーション

- 10 件ごと。UI は「次へ」「前へ」ボタンのみ (番号付きページャは設けない)
- 1 ページ目は `/blog` および `/blog/tags/…` (`/page/1` は生成しない。`/page/1` への到達時は 1 ページ目へ正規化)
- SSG のため各ページを個別に prerender する

## レイアウトと Marginalia

Blog ページは「アイコンナビ + 左サイドツリー + メインコンテンツ」の構成を取る (右サイドバー = 目次・バックリンクは持たない)。一覧系だが、本文の Marginalia を表示するためメインコンテンツは左右ガターを確保する。

- メインコンテンツは詳細ページ相当の 3 段 grid (`左ガター / 本文 / 右ガター`) を用いる
- **Marginalia (脚注 / Callout) は既存の詳細ページと完全に同等の挙動**とする
  - 広い (≥1280px): 左右両ガターに `data-side` で振り分けて float
  - 中 (1024–1279px): 右ガターのみに float
  - 狭い (≤1023px): 脚注は各記事末尾の `FootnoteSection` にまとめ、Callout はインライン展開
- 記事ブロックの境界で `clear` し、前後の記事の Marginalia が混ざらないようにする。左右振り分け (`assignMarginaliaSides`) は記事単位で document order を初期化する
- 区切り線 (`---`) で記事ブロックを視覚的に分離する

## Markdown 拡張記法

Blog 本文は既存 Notes と**同じフルセット**の拡張記法をサポートする。

- `[[wiki-link]]` — **外向きのみ**。記事内のリンクは Notes / Glossary / Books へ解決する。解決ルールは `docs/build-spec.md` 準拠 (非公開・未解決はテキスト化)
- `![[embed]]` — 1 階層展開。Embed 先は Notes / Glossary / Books
- `> [!type]` Callout — 5 種別 + `private` 除外。Marginalia として表示
- `[^n]` 脚注 — Marginalia として表示
- コードブロック — Shiki ハイライト
- 画像 `![[image.png]]` — Vault からコピー

### リンクグラフへの参加 (外向きのみ)

Blog は個別 URL (詳細ページ) を持たないため、**リンクの受け手にはならない**。

- 記事内の `[[…]]` は Notes / Glossary / Books へ解決する (外向き)
- Blog 記事自身は他コンテンツの `[[…]]` のリンク先候補に**ならない**。リンク解決のインデックスには登録しない
- 他コンテンツ詳細ページの**バックリンク欄に Blog は出さない** (Blog をリンクグラフのソースとして数えない)

## グローバル統合

| 箇所                       | 対応                                                                        |
| -------------------------- | --------------------------------------------------------------------------- |
| アイコンナビ (IconNav)     | Blog アイコンを追加 (Notes / Glossary / Books に続く 4 つ目)                 |
| トップ「最近更新」         | Blog 記事も横断対象に含める (`updated` 降順)。リンク先は記事の全タグ集合ページ (正規形) + アンカー |
| トップ「コンテンツ入口」   | Blog の入口カードを追加 (公開記事件数を表示)                                 |
| トップ「Featured」         | Blog は対象外 (`featured` を持たない)                                        |
| フィード                   | `/blog/feed.xml` (Atom) を生成                                              |
| sitemap                    | 生成した全タグ集合ページ + ページネーション + `/blog` 系を含める             |

### フィード (`/blog/feed.xml`)

- Atom 形式。公開記事を作成日時降順で最新 N 件 (初期値 20、実装時に確定)
- 各エントリ:
  - `title` — タグ併記 (`#t1#t2…`、コードポイント昇順)
  - `id` / `link` — 記事の全タグ集合ページ (正規形) URL + 記事アンカー
  - `published` — 作成日時 (ファイル名由来)
  - `updated` — frontmatter の `updated`
  - 本文 — ビルド時に本文先頭から生成した抜粋 (または本文 HTML。実装時に確定)

> Blog 専用フィードを設ける一方で、コンセプト上の主動線はあくまでタグツリーによる回遊とする。フィードは補助的な購読手段の位置づけ。

## 既存仕様との主な差分

- コンテンツタイプが 4 種に増える (`ContentType = "notes" | "glossary" | "books" | "blog"`)
- 「タグの組み合わせ = ページ」という、他タイプにない URL モデルを持つ
- 記事に個別詳細ページ・タイトル・summary・featured がない
- 作成日時をファイル名から取得する (frontmatter `created` を持たない唯一のタイプ)
- タグ集合ごとに正規形 1 ページのみを生成する (順列による重複ページを作らない)。URL はタグを `+` 連結した単一セグメント
