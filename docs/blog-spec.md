# Blog 仕様

「よりストック型の、フローしないブログ」をコンセプトとした 4 つ目のコンテンツタイプ **Blog** の仕様を定義する。Obsidian Vault の `Blog/` フォルダをソースとし、**タグの組み合わせ自体がページ (URL) となる**点が、既存の Notes / Glossary / Books と根本的に異なる。

本ドキュメントは Blog 固有の仕様に限定する。frontmatter スキーマの全体像は `docs/content-spec.md`、レイアウトの基本は `docs/ui-spec.md`、ビルドパイプラインは `docs/build-spec.md` を参照。

## コンセプト

- 時系列で「流れていく」通常のブログではなく、タグのネットワークによって記事を回遊させる構造を取る
- 個々の記事は **タイトルを持たず**、付与されたタグの組み合わせが実質的なタイトルとなる
- 記事は個別の詳細ページを持たない。常に「タグの組み合わせページ内のひとつのブロック」として表示される

## ソースとデータモデル

### 配置

| 項目         | 内容                                                          |
| ------------ | ------------------------------------------------------------- |
| Vault 内パス | `Blog/` (設定ファイルで指定)                                  |
| 構造         | フラット (サブフォルダなし)。ファイルは `Blog/` 直下に置く    |
| 除外         | Notes 収集の `exclude` に `Blog/**` を追加する                |

### ファイル名 = 作成日時 (source of truth)

記事の**作成日時はファイル名を唯一の正**とする。frontmatter に `created` は持たせない (二重管理を避けるため)。

- フォーマット: `YYYY-MM-DD HHmm` (例: `2025-12-11 0930.md`)
  - Obsidian / OS のファイル名制約のため `:` は使わず、時刻は 4 桁連結 (`HHmm`) とする
  - タイムゾーンはサイトロケール (JST 固定、`site.config.ts` で上書き可) として扱う
- 用途:
  - **並び順**: Blog 内のすべての一覧は作成日時降順。時刻まで含むため同日複数記事も安定ソートされる
  - **表示**: 記事ブロックに表示する「作成日」はファイル名の日付部分を `YYYY/MM/DD` に整形したもの
  - **アンカー**: ファイル名から各記事の HTML アンカー id を生成する (後述)
- 一意性: 同一フォルダ内でファイル名は重複できないため、作成日時は自然に一意となる

### frontmatter スキーマ

Blog ではすべてのメタデータを **必須** とする (既存タイプは `status` 等が任意だが、Blog は明示を要求する)。

| キー      | 型              | 必須 | 説明                                                                     |
| --------- | --------------- | ---- | ------------------------------------------------------------------------ |
| `tags`    | string[]        | 必須 | 1〜4 個 (トークン数)。階層タグ可 (`A/B`、深さ 2 まで)。実質的なタイトルを兼ねる |
| `updated` | date (ISO 8601) | 必須 | 更新日。sitemap の `lastmod`、グローバルトップの「最近更新」、feed に使用 |
| `status`  | enum            | 必須 | `published` / `draft` / `archived`。`draft` / `archived` は完全に除外    |

- `title` / `summary` / `featured` / `created` は **持たない**
  - タイトル: タグの組み合わせが代替する
  - サマリー: feed 等で必要な抜粋はビルド時に本文先頭から自動生成する
  - Featured: Blog は Featured セクションの対象外
  - created: ファイル名から取得 (上記)

### バリデーション (build.strict)

以下はビルドエラーとする。

- ファイル名が `YYYY-MM-DD HHmm` 形式でない / 無効な日時
- `tags` が空、または 5 個以上 (**1 記事あたり最大 4 タグトークン**。階層タグも 1 トークンと数える)
- 階層タグの深さが 3 以上 (`A/B` まで可、`A/B/C` 以上は不可)
- タグの空セグメント (先頭/末尾/連続する `/`、例 `/A`・`A/`・`A//B`)
- タグセグメントに `+` を含む (集合区切りと衝突)
- タグセグメントに `--` を含む / セグメントが `-` で始まる・終わる (階層エスケープとの曖昧さ回避。単独の `-` は可、例 `UI-UX`)
- タグセグメントが予約語 `page` (ページネーション用セグメントと衝突するため)
- `updated` / `status` の欠損・型不一致・enum 違反

警告 (継続) とするもの: 本文が空。

## タグ

### 名前空間

タグはコンテンツタイプごとに独立した名前空間を持つ。Blog の `#react` は Notes / Glossary / Books の `#react` とは別物として扱い、URL も `/blog/tags/react` で分離する。

### 階層タグ (実サブタグ)

Blog タグは Obsidian と同様に `/` 区切りの**階層タグ** (`A/B`) をサポートする。階層タグは「実サブタグ」として扱う。

- **ファセット (絞り込みの単位)**: タグトークン `A/B` は、その全プレフィックス `A` と `A/B` をファセットとして提供する。記事のファセット集合は全トークンのプレフィックスの和。例: `#UI-UX/デザインシステム` を持つ記事のファセットは `{UI-UX, UI-UX/デザインシステム}`
- **親は拾い、葉単独は拾わない**: 親ファセット `#UI-UX` のページはこの記事を含む (プレフィックス一致)。一方、葉セグメント `デザインシステム` は単独ファセットには**ならない**ため、`/blog/tags/デザインシステム` (単独) はこの記事を含まない。これにより「葉をトップ階層へ昇格させない」が成立する
- 深さは **2 まで** (`A/B`)。`A/B/C` 以上はビルドエラー (バリデーション参照)
- `+` は集合区切り、`--` は階層エスケープ (URL 構造参照) に使うため、タグセグメントに含めることを禁止する

### 並び順 (正規形の基準)

タグ・ファセットの並び順は **Unicode コードポイント昇順** とする。

- 左サイドツリーの同階層内のソート、および「それ以外のタグ」併記時の順序に一律で適用する
- 階層ファセットは**論理パス文字列** (`/` 連結) のコードポイント比較で並べる (例: `UI-UX/デザインシステム` < `UI-UX/マイクロコピー`)
- Latin → カタカナ → 漢字 の順になる (例: `UI-UX` < `スターウォーズ` < `デザインシステム` < `マイクロコピー` < `ライティング` < `映画`)
- この順序がファセット集合の **正規形 (URL に用いる唯一の並び)** を一意に決定する

## URL 構造

トレイリングスラッシュなし。

| URL                              | 内容                                                                          |
| -------------------------------- | ----------------------------------------------------------------------------- |
| `/blog`                          | トップページ (全公開記事を作成日時降順)                                        |
| `/blog/page/[n]`                 | トップのページネーション (`n` は 2 以上)                                       |
| `/blog/tags/[tagset]`            | タグ詳細ページ。`tagset` はファセット集合 (1〜4 個) を正規形で連結した単一セグメント |
| `/blog/tags/[tagset]/page/[n]`   | タグ詳細のページネーション (`n` は 2 以上)                                     |
| `/blog/feed.xml`                 | Blog 専用 Atom フィード                                                        |

- `tagset` は **単一セグメント**で、文法は `tagset = facet (+ facet)*`、`facet = segment (-- segment)*`
  - **集合の区切りは `+`**、**階層の区切りは `--`** (既存タイプの `/`→`--` エスケープと整合)。例:
    - `{UI-UX}` → `UI-UX`
    - `{UI-UX/デザインシステム}` → `UI-UX--デザインシステム`
    - `{映画, スターウォーズ}` → `スターウォーズ+映画`
    - `{映画, UI-UX/デザインシステム}` → `UI-UX--デザインシステム+映画`
  - パスセグメント内の `+` はリテラル文字 (クエリ文字列で空白に変換される挙動とは別で、`decodeURIComponent` でも変化しない)。`/` を使わず `--` でエスケープすることで `tagset` 全体を 1 セグメントに保てる
  - 各セグメント名は URL にそのまま用いる (日本語可、非エスケープ)。`+` / `--` をセグメントに含めることは禁止 (バリデーションで弾く)
- 正規形: ファセットを論理パス文字列のコードポイント昇順で並べ `+` 連結する。**冗長な祖先ファセットは落とす** (`{UI-UX, UI-UX/デザインシステム}` は後者が前者を含意するので `{UI-UX/デザインシステム}` に正規化)
- ファセット集合ごとに生成するページは **正規形 1 つだけ**。非正規 (未ソート・冗長) のトークンは生成しないため到達時は 404 となる (詳細は後述)
- `/blog/tags` (タグなし) は生成しない。タグ一覧は左サイドツリーが担う
- `page` はページネーション専用の予約セグメント。タグセグメントに `page` は使えない (バリデーションで弾く)

### タグ詳細ページの絞り込み条件

`tagset` のファセット集合を S とすると、そのページには **S を部分集合として含む (記事のファセット集合 ⊇ S) すべての公開記事**を作成日時降順で表示する。

- 例: `/blog/tags/映画` → ファセット `映画` を持つ全記事
- 例: `/blog/tags/スターウォーズ+映画` → `映画` と `スターウォーズ` の**両方**を持つ全記事 (他のタグを併せ持っていてもよい)
- 例: `/blog/tags/UI-UX` → ファセット `UI-UX` を持つ全記事。`#UI-UX` を直接持つ記事に加え、**`#UI-UX/…` の階層タグを持つ記事も含む** (プレフィックス一致)
- 例: `/blog/tags/UI-UX--デザインシステム` → ファセット `UI-UX/デザインシステム` を持つ記事 (= `#UI-UX/デザインシステム` タグの記事)。`#UI-UX` と `#デザインシステム` を別々のフラットタグで持つ記事は**含まない** (それらは `UI-UX/デザインシステム` ファセットを持たない)

### 集合ごとに単一ページ (正規形)

ファセット集合 S が同一で並び順だけが異なる表記 (順列) は絞り込み結果が完全に一致するため、**ファセット集合ごとに正規形のページを 1 つだけ生成**し、順列の重複ページは生成しない。

- **正規形** = S のファセットを **論理パス文字列のコードポイント昇順**に並べ、冗長な祖先を落として `+` 連結した `tagset` セグメント
- 順序違い・冗長祖先込みなど非正規の表記は生成しない。到達時は (静的サイトのため) 404 とする
- 後述の左サイドツリー・パンくず・「それ以外のタグ」などサイト内のリンクは**すべて正規形 URL を指す**ため、非正規 URL は外部リンクや手入力でのみ発生する
- 例: `{スターウォーズ, 映画}` のページは `/blog/tags/スターウォーズ+映画` ただ 1 つ (`ス` < `映`)

`rel=canonical` や noindex といった重複ページ向けの SEO 制御は不要となる (重複ページ自体を作らないため)。

> [!note]
> 「同一記事が複数のファセット集合ページに載る」重複は依然として残る (例: ファセット `{a, b, c}` を持つ記事は `{a}` `{a, b}` `{a, b, c}` 等すべての部分集合ページに出現する)。ただしこれらは**絞り込み結果が異なる別ページ**であり、内容が完全一致する「順列の重複」とは異なる。検索インデックスの重複排除のみ後述の対応が必要で、canonical は不要。

#### 生成するファセット集合ページの定義

- ファセット集合 S (どのファセットも他のファセットのプレフィックスでない **antichain**) について「S を部分集合として含む公開記事が 1 件以上存在する」とき、かつそのときに限り `/blog/tags/[S の正規形]` を生成する
- antichain のサイズはトークン数を超えないため (同一トークンのプレフィックス同士は一方が他方を含意し共存しない)、生成対象 S のサイズは自然に 1〜4 に収まる
- ある集合 S のページが存在するなら、S の任意の部分集合のページも必ず存在する (同じ記事がその部分集合の上位集合になるため)。これによりパンくずの累積リンク (後述) は常に到達可能
- **生成ページ集合 = 左サイドツリーのノードが実現するファセット集合と一致する** (lock-step)。ツリーが階層で整形される結果、昇格しない葉単独のページ (`/blog/tags/デザインシステム` を `#UI-UX/デザインシステム` だけが裏付ける場合) は生成されず、孤立ページが出ない

> [!note]
> 厳密には lock-step (直前の項目) には例外がある。1 記事が同じ親の複数の兄弟サブタグ (`A/B` と `A/C` など) を持つ場合、ファセット集合 `{A/B, A/C}` のページは定義どおり生成されるが、共起ツリーには現れない。ツリーの階層降下は親ファセット `A` を子 `A/B` または `A/C` へ深める操作で、いずれの経路も antichain ガードにより `A` を再取得できず、もう一方の兄弟サブタグへ降下する枝が存在しないため。このページは記事の「それ以外のタグ」クラスタリンクから実 `<Link>` として到達できる (トップページなら記事の全タグトークンの併記が `canonical({A/B, A/C})` を直接指す) ため crawlLinks によるプリレンダー漏れはなく本番 404 にはならないが、ツリーには現れず、表示中にアクティブ表示されるツリーノードも無い。より正確な不変条件は「生成される各ページは、ツリーか記事のクラスタリンクのいずれか実 `<Link>` から到達可能」であり、これにより SSG (crawlLinks) での全ページ生成は保証される。

- ビルド削減: 順列ではなく集合 (antichain) ベースで数えるため、フラットのみの記事 (m タグ) では順列 ΣP(m, k) (m=4 で 64 経路) → 2^m − 1 (m=4 で 15) に減る。サイト全体では集合の重複排除でさらに減少する

### sitemap / 検索への反映

- **sitemap**: 生成したすべてのファセット集合ページ (とそのページネーション) および `/blog`・`/blog/page/[n]` を含める。各ページは絞り込み結果の異なる固有ページなので、すべて掲載対象
- **検索 (Pagefind)**: 同一記事が複数のファセット集合ページに重複出現するため、各記事本文のインデックス対象は**その記事の全ファセット集合ページ (= 最も特定的な正規形ページ) の 1 箇所のみ**とする。他のページ (より広い部分集合ページ・`/blog` 系) では当該記事ブロックを `data-pagefind-ignore` にする。検索結果のリンク先は全ファセット集合ページ + 記事アンカー

## 左サイドメニュー (タグツリー)

Blog 選択時、左サイドバーにはファイルツリーではなく**タグの共起ツリー**を表示する。

### 構築ルール

記事が持つタグの**共起の順列**を展開する。階層タグはそこに**有向のネスト**を加える。各ノードはファセット集合 (antichain) に対応し、その正規ページへリンクする。

- **トップレベル**: **昇格した深さ 1 のファセット**。昇格 = あるトークンの**フラット (`#A`) または根 (`#A/…`)** として出現すること。階層タグの**葉セグメントは昇格しない** (例: `#UI-UX/デザインシステム` だけでは `デザインシステム` はトップに出ない)
- **子ノード**: あるノードの現ファセット集合を S とすると、子は次の 2 種:
  - **階層降下 (有向)**: S 内のファセット `A` を `A/B` に深める。`A/B` ファセットを持つ公開記事が S を満たすとき生成 (深さ 2 まで)
  - **共起追加 (順列)**: S に別トークンの根ファセット `D` を足す。`S ∪ {D}` を満たす公開記事が存在するとき生成
  - いずれも結果のファセット集合は antichain (冗長な祖先は持たない)
- ノードは「対応するファセット集合を満たす公開記事が 1 件以上存在する」ときに限り生成する
- 同階層の兄弟は、各子が親に対して**追加するファセットの論理パス文字列**のコードポイント昇順でソートする (階層子 `A/X` は `A/…` で始まるため、共起子との相対順序もこの 1 規則で一意に決まる)
- ノードのラベルは追加された末尾セグメント (例: `A/B` を深めた子のラベルは `B`)
- ツリーの最大深さは「共起追加 (最大 4) + 階層降下の追加段 (1 トークンあたり深さ 2 なら +1)」で決まり、おおむね 8 段が上限

複数タグを持つ記事は、各タグがトップレベルに現れ、その配下に残りのタグがネストされるため、項目は意図的に重複する (下記イメージ参照)。階層タグはこの重複を**一方向に限定**する: `#A/B` は `A` 配下に `B` を作るが、`B` をトップに昇格させず、`B` 配下に `A` を作りもしない。

> [!note]
> 同一ペア (例 UI-UX, デザインシステム) を**共起** (`#UI-UX` + `#デザインシステム`) と**階層** (`#UI-UX/デザインシステム`) の両方で表現すると、`UI-UX` 配下に同名ラベル `デザインシステム` のノードが 2 つ並ぶ (共起子 → 集合ページ `UI-UX+デザインシステム` / 階層子 → 階層ページ `UI-UX--デザインシステム`)。両者は別記事を指す別ページ。タグ付けを一貫させれば回避できる。

#### イメージ A (記事例: `{UI-UX, マイクロコピー, ライティング}` `{UI-UX, デザインシステム}` `{UI-UX}` `{スターウォーズ, 映画}`)

```
- UI-UX
  └ デザインシステム
  └ マイクロコピー
    └ ライティング
  └ ライティング
    └ マイクロコピー
- スターウォーズ
  └ 映画
- デザインシステム
  └ UI-UX
- マイクロコピー
  └ UI-UX
    └ ライティング
  └ ライティング
    └ UI-UX
- ライティング
  └ UI-UX
    └ マイクロコピー
  └ マイクロコピー
    └ UI-UX
- 映画
  └ スターウォーズ
```

> 元の手描きイメージではトップレベルの一部 (`マイクロコピー` / `ライティング` 配下) が 2 階層までしか描かれていなかったが、ルール上は最下層まで完全展開する。上記が正となる。

#### イメージ A2 (階層タグ。記事例: source A = `#UI-UX` `#デザインシステム` / source B = `#UI-UX/デザインシステム`)

```
- UI-UX
  └ デザインシステム   → /blog/tags/UI-UX--デザインシステム  (階層 / source B)
  └ デザインシステム   → /blog/tags/UI-UX+デザインシステム   (共起 / source A)
- デザインシステム
  └ UI-UX             → /blog/tags/UI-UX+デザインシステム   (共起 / source A)
```

- `デザインシステム` がトップに出るのは source A (フラット `#デザインシステム`) による。source B は `デザインシステム` をトップに昇格させない
- `デザインシステム` 配下に `UI-UX` が来るのは source A の共起のみ。source B (階層) は一方向 (`UI-UX → デザインシステム`) なので、ここには現れない
- `UI-UX` 配下の 2 つの `デザインシステム` は別ページを指す (階層 = 階層ページ / 共起 = 集合ページ)。これが前述の「同名ノードが 2 つ並ぶ」ケース。並び順は追加ファセットの論理パス基準で、`UI-UX/デザインシステム` (`U`) が `デザインシステム` (`デ`) より前に来る

### ツリーの挙動

- 各タグノードはリンクであり、クリックでそのノードのファセット集合の**正規ページ**へ遷移する。ツリー上の表示順 (順列) に関わらず、リンク先 URL は常に正規形 (`--` 階層 / `+` 集合) となる
  - 順列ツリーは意図的な重複を残し「同一集合への複数の入口」= 回遊性を担保するが、行き先 (ページ) は集合ごとに 1 つに収束する
- **アクティブ表示 (ハイライト)**: 現在ページのファセット集合と一致する**すべてのノード**に付与する。URL のファセット集合から導出する**ステートレスな処理**とし、遷移経路には依存しない
  - 非正規順のノードをクリックして正規ページへ遷移しても、クリック元ノードは一致集合に含まれるため点灯したままとなる。強調が別の枝へ「移動」することはなく、正規順の双子ノードが追加で点灯するだけ
- **展開 (開閉)**: ハイライトとは独立に扱う
  - クライアント遷移中はユーザーの開閉状態を保持する。操作していた枝が開いたまま残り、クリック元の点灯ノードが可視のまま維持される
  - コールド読み込み (リロード・外部リンクで正規 URL に直接到達) 時は、現在集合の**正規チェーンのみ**を既定展開する
  - 一致する順列の双子ノードを強制展開はしない (複数枝が一斉に開いて賑やかになるのを避ける)
- ツリー上部に検索 (フィルタ) 入力を置き、タグ名でツリーをフィルタする (既存ツリーと同様)
- react-aria-components の Tree を用い、キーボード操作・ARIA 属性を付与する

## ページ仕様

### 記事ブロックの構成

トップページ・タグ詳細ページとも、各記事を以下の構成のブロックとして縦に並べる。ブロック間は区切り線 (`---`) で仕切る。

1. **作成日** — `YYYY/MM/DD` (ファイル名の日付部分)
2. **それ以外のタグ** — 現在ページのファセットで未指定の、記事のタグトークンを併記 (リンク)。該当がなければ省略。階層タグは、現在ページが親ファセットを含むなら残りのセグメントのみ表示する (例: `/blog/tags/UI-UX` 上では `#UI-UX/デザインシステム` の記事を `#デザインシステム` と表示)。併記全体が 1 つのリンク (クラスタ単位)。リンク先は「リンク遷移ルール」を参照
3. **本文** — Markdown を変換した HTML (拡張記法は後述)

「それ以外のタグ」が実質的に通常ブログの記事タイトルの役割を果たす。

### トップページ (`/blog`)

- パンくず: `Blog`
- 全公開記事を作成日時降順で表示
- 各記事の「それ以外のタグ」= その記事の**全タグトークン** (現在ページのファセットが空のため)。階層タグはフルパス表記 (`#UI-UX/デザインシステム`)。コードポイント昇順で併記
- 10 件ごとにページング (`/blog/page/[n]`、「次へ」「前へ」のみ)

#### イメージ C (トップの記事タグをクリックした先 = 正規タグページ `/blog/tags/UI-UX+マイクロコピー+ライティング`)

```
Blog › #UI-UX › #UI-UX#マイクロコピー › #UI-UX#マイクロコピー#ライティング (パンくず)

#UI-UX#マイクロコピー#ライティング (ページタイトル)

2025/12/11

{本文}

---

2025/04/09

{本文}
```

### タグ詳細ページ (`/blog/tags/…`)

- パンくず: 累積正規チェーン `Blog / #f1 / #f1#f2 / … / #f1#f2…fk` (ファセット集合を正規順に並べ、先頭から 1 つずつ足した部分集合を順に表示)
  - 各要素はその部分集合の正規ページへリンクする (表示は `#` 連結のフルパス、リンク先 URL は `--`/`+` の正規形)。末尾要素は現在ページ
  - 生成定義より部分集合ページは必ず存在するため、各リンクは常に到達可能 (階層ファセット内の途中段は挟まない簡潔版)
- ページタイトル: `#f1#f2…` (ファセットを正規順で併記。階層はフルパス `#UI-UX/デザインシステム`)
- 絞り込み: ファセット集合 ⊇ このページのファセット集合 となる公開記事を作成日時降順で表示
- 各記事の「それ以外のタグ」= 記事のタグトークンから、このページのファセットで指定済みのものを除いた残り。コードポイント昇順で併記
- 10 件ごとにページング (`/blog/tags/[tagset]/page/[n]`)

#### イメージ B (`/blog/tags/UI-UX`)

```
Blog › #UI-UX (パンくず)

#UI-UX (ページタイトル)

2025/12/11
#マイクロコピー#ライティング

{本文}

---

2025/10/29
#デザインシステム

{本文}

---

2025/07/24

{本文}

---

2025/04/09
#マイクロコピー#ライティング

{本文}
```

`2025/07/24` は `#UI-UX` のみを持ち「それ以外のタグ」が存在しない記事の例。

### 記事アンカー

各記事ブロックは、ファイル名 (作成日時) 由来の安定したアンカー id を持つ。全ページで同一の id を用いる。

- 例: ファイル `2025-12-11 0930.md` → `id="p-2025-12-11-0930"` (空白等は URL/HTML 安全な文字へ正規化)

### リンク遷移ルール

「それ以外のタグ」クラスタおよびトップページの記事タイトル相当クリック時の遷移先を以下で統一する。

現在ページのファセット集合を P、クリック対象の併記タグ (トークン) 群を R とすると、

> 遷移先 = `/blog/tags/` + `canonical(P ∪ R)` (正規順・冗長祖先を落とした正規形) [ + `/page/[n]` ] + `#記事アンカー`

- 遷移先は常にファセット集合 `canonical(P ∪ R)` の**正規ページ**。集合の和を取り antichain 正規化するだけなので、常に生成済みのページへ着地する
  - 例 1: `/blog/tags/映画` で `#スターウォーズ` をクリック → `/blog/tags/スターウォーズ+映画`
  - 例 2: `/blog/tags/UI-UX` で `#マイクロコピー#ライティング` をクリック → `/blog/tags/UI-UX+マイクロコピー+ライティング`
  - 例 3 (階層): `/blog/tags/UI-UX` で `#デザインシステム` (= 階層タグ `UI-UX/デザインシステム` の記事) をクリック → `canonical({UI-UX, UI-UX/デザインシステム})` = `/blog/tags/UI-UX--デザインシステム` (冗長な `UI-UX` は脱落)
- **トップページから**: P は空集合のため、遷移先は「記事の全タグトークンを正規順に並べた正規ページ」+ 該当記事アンカーとなる
  - 例: トップの `2025/12/11` の `#UI-UX#マイクロコピー#ライティング` をクリック → イメージ C の `2025/12/11` の位置へ
- 「それ以外のタグ」併記は 1 クリックで R 全体を追加する単位とする (タグ個別ではなく、クラスタごと)
- 遷移先で対象記事が 2 ページ目以降にある場合、リンクは正しい `/page/[n]` + アンカーを指す (ビルド時に算出)

### ページネーション

- 10 件ごと。UI は「次へ」「前へ」ボタンのみ (番号付きページャは設けない)
- 1 ページ目は `/blog` および `/blog/tags/…` (`/page/1` は生成せず、サイト内からリンクもしないため到達時は 404)
- SSG のため各ページを個別に prerender する

## レイアウトと Marginalia

Blog ページは「アイコンナビ + 左サイドツリー + メインコンテンツ」の構成を取る (右サイドバー = 目次・バックリンクは持たない)。一覧系だが、本文の Marginalia を表示するためメインコンテンツは左右ガターを確保する。

- メインコンテンツは詳細ページ相当の 3 段 grid (`左ガター / 本文 / 右ガター`) を用いる
- **Marginalia (脚注 / Callout) は既存の詳細ページと完全に同等の挙動**とする
  - 広い (≥1280px): 左右両ガターに `data-side` で振り分けて float
  - 中 (1024–1279px): 右ガターのみに float
  - 狭い (≤1023px): 脚注は各記事末尾の `FootnoteSection` にまとめ、Callout はインライン展開
- 記事ブロックの境界で `clear` し、前後の記事の Marginalia が混ざらないようにする。左右振り分け (`assignMarginaliaSides`) は記事単位で document order を初期化する
- 区切り線 (`---`) で記事ブロックを視覚的に分離する

## Markdown 拡張記法

Blog 本文は既存 Notes と**同じフルセット**の拡張記法をサポートする。

- `[[wiki-link]]` — **外向きのみ**。記事内のリンクは Notes / Glossary / Books へ解決する。解決ルールは `docs/build-spec.md` 準拠 (非公開・未解決はテキスト化)
- `![[embed]]` — 1 階層展開。Embed 先は Notes / Glossary / Books
- `> [!type]` Callout — 5 種別 + `private` 除外。Marginalia として表示
- `[^n]` 脚注 — Marginalia として表示
- コードブロック — Shiki ハイライト
- 画像 `![[image.png]]` — Vault からコピー

### リンクグラフへの参加 (外向きのみ)

Blog は個別 URL (詳細ページ) を持たないため、**リンクの受け手にはならない**。

- 記事内の `[[…]]` は Notes / Glossary / Books へ解決する (外向き)
- Blog 記事自身は他コンテンツの `[[…]]` のリンク先候補に**ならない**。リンク解決のインデックスには登録しない
- 他コンテンツ詳細ページの**バックリンク欄に Blog は出さない** (Blog をリンクグラフのソースとして数えない)

## グローバル統合

| 箇所                       | 対応                                                                        |
| -------------------------- | --------------------------------------------------------------------------- |
| アイコンナビ (IconNav)     | Blog アイコンを追加 (Notes / Glossary / Books に続く 4 つ目)                 |
| トップ「最近更新」         | Blog 記事も横断対象に含める (`updated` 降順)。リンク先は記事の全ファセット集合ページ (正規形) + アンカー |
| トップ「コンテンツ入口」   | Blog の入口カードを追加 (公開記事件数を表示)                                 |
| トップ「Featured」         | Blog は対象外 (`featured` を持たない)                                        |
| フィード                   | `/blog/feed.xml` (Atom) を生成                                              |
| sitemap                    | 生成した全ファセット集合ページ + ページネーション + `/blog` 系を含める       |

### フィード (`/blog/feed.xml`)

- Atom 形式。公開記事を作成日時降順で最新 N 件 (初期値 20、実装時に確定)
- 各エントリ:
  - `title` — タグ併記 (`#f1#f2…`、正規順。階層はフルパス `#UI-UX/デザインシステム`)
  - `id` / `link` — 記事の全ファセット集合ページ (正規形) URL + 記事アンカー
  - `published` — 作成日時 (ファイル名由来)
  - `updated` — frontmatter の `updated`
  - 本文 — ビルド時に本文先頭から生成した抜粋 (または本文 HTML。実装時に確定)

> Blog 専用フィードを設ける一方で、コンセプト上の主動線はあくまでタグツリーによる回遊とする。フィードは補助的な購読手段の位置づけ。

## 既存仕様との主な差分

- コンテンツタイプが 4 種に増える (`ContentType = "notes" | "glossary" | "books" | "blog"`)
- 「タグの組み合わせ = ページ」という、他タイプにない URL モデルを持つ
- 記事に個別詳細ページ・タイトル・summary・featured がない
- 作成日時をファイル名から取得する (frontmatter `created` を持たない唯一のタイプ)
- ファセット集合ごとに正規形 1 ページのみを生成する (順列による重複ページを作らない)。URL は集合を `+`・階層を `--` で連結した単一セグメント
- 階層タグ (`A/B`、深さ 2 まで) を「実サブタグ」として扱う。親ファセットは子を拾い、葉単独は拾わない (Obsidian 準拠)。階層はツリーの一方向ネストにも反映する

## 実装時に確定した事項

- ファイル名日時は `YYYY-MM-DD HHmm` の厳格一致のみ (秒なし、区切り文字のゆらぎ不可)。正規表現 + 実在日時チェック
- feed エントリの本文は抜粋 (既存 `extractFeedSummary`、本文 HTML strip + 200 grapheme)
- Pagefind の重複排除: 記事ブロック本文の div に「現在ページ = その記事の全ファセット集合ページ (正規形)」のときのみ `data-pagefind-body` を付与する。作成日見出し `<h2 id="p-…">` を各記事に置き、sub-result でアンカー付きの検索結果リンクを得る
- 記事アンカー id はファイル名 stem の空白を `-` に置換し `p-` を前置 (`2025-12-11 0930` → `p-2025-12-11-0930`)。ファイル名フォーマットが厳格なため追加の正規化は不要
- frontmatter に `title` / `summary` / `featured` / `created` が書かれていた場合はビルドエラー (「持たない」キーの混入を許さない)
- `/page/1` へのリダイレクトは行わない (サイト内リンクは 1 ページ目を常に `/blog` / `/blog/tags/[tagset]` に向けるため、`/page/1` は生成されず 404 となる)
